    Branch protection (beta / stable)

    Configure in GitHub Settings → Rules → Rulesets. Classic branch protection is not used. develop has no required checks: direct push stays allowed.

    The only list of check contexts is .github/required-checks.json. .github/branch-ruleset-beta-stable.json is the ruleset body for release-lines (ruleset id 24311415). .github/workflows/required-checks.yml fails when those two files disagree, or when a context does not match a workflow job. On a schedule it also compares the live rules for beta and stable.

    Ruleset: release-lines (beta, stable)

    Rule Value
    Restrict updates / deletions yes
    Block force pushes yes
    Require a pull request before merging yes (1 approval, stale reviews dismissed, threads resolved)
    Require status checks to pass yes, strict
    Required checks merge-gate, rps (ubuntu-26.04), rps (windows-latest), rps (macos-15), gitleaks, dependency-review, tests-or-waiver, guard-nc-paths, cla, install-smoke (windows-latest), install-smoke (ubuntu-latest), install-smoke (macos-latest), install-smoke (ubuntu-24.04-arm), release-dry-run
    Code scanning CodeQL, high-or-higher security alerts, error alerts
    Admin bypass repository admin role, pull request only (no direct push)

    merge-gate is the single .NET context. It passes when build, redis-fleet, ui-portable (all three OS), and cli-e2e (all three OS) succeed. A docs-only pull request skips those four jobs and merge-gate still reports success, so the ruleset does not wait forever. build, ui-portable (...), and cli-e2e (...) are not required contexts: Deploy website also has a job named build.

    Apply after a promotion pull request has shown merge-gate green:

    gh api -X PUT repos/justcoding121/titanium-web-proxy/rulesets/24311415 --input .github/branch-ruleset-beta-stable.json

    Promotion heads

    Promotion pull requests use head branch release/<version>-to-<channel> created from develop (for example release/809-to-beta). Do not open the promotion from a long-lived develop push tip: the dry-run concurrency group is per PR and cancel-in-progress is on for pull_request, so ordinary develop merges would cancel an in-flight dry-run on a develop-based head.

    The signing environment deployment-branch policy may list exact names or wildcards such as release/*. tools/ci/assert-signing-environment.sh matches with fnmatch. Today the environment admits all branches (deployment_branch_policy: null); if that tightens, add a release/* policy before the next promotion.

    Release ladder

    1. Pull request into beta or stable. The ruleset above, plus the CodeQL rule. rps runs compare-spot on three OS. inspector-install-smoke runs all five legs (windows-latest, ubuntu-latest, macos-latest, macos-15-intel, ubuntu-24.04-arm). Required contexts are the three primary OS legs plus ubuntu-24.04-arm. macos-15-intel stays continue-on-error (fresh Safari decrypt GET miss on the Intel image; fresh omits Safari, upgrade-verify still includes it). update-under-decrypt and in-app-apply are hard gates on every leg. New product-smoke lifecycle steps use enforce.sh / LIFECYCLE_ENFORCE (soft until the repo variable is true). release-dry-run builds, signs, notarizes, and smokes Inspector, CLI, Plus, the control-plane images, and the packaged Helm charts on the PR merge commit. Same-repository heads only. There is no waiver label on required checks. The author of the release pull request fixes a red run on that branch. Do not merge it with an admin bypass. Strict status checks stay on, so the base cannot move between the green dry-run and the merge.
    2. Push to beta or stable. .NET runs merge-gate, then rps-publish-gate (edition comparison) and rps-peer-gate (spot matrix) on the merge commit. Those push jobs are the evidence on the release SHA, because pull-request checks attach to the PR head, not the merge commit. cut-product-tag and publish-nuget refuse to move a tag or push a package unless a successful release-dry-run recorded the same git tree. A maintainer can pass evidence_override with a reason; that opens an escaped-defect issue. cut-product-tag then dispatches release.yml. The readiness workflows (conformance, soak, kubernetes-smoke, inspector-unattended, fuzz-nightly, dast, inspector-install-smoke) also run on that push.
    3. release.yml. release-readiness waits for those workflows on the same SHA. A dry-run skips that wait. A dry-run also skips gate-evidence, test, and cli-e2e: the PR .NET merge-gate already covered the same merge-ref tree, and tree evidence still binds the dry-run to the merged tree. On a real cut, gate-evidence records whether the push .NET run already passed merge-gate, rps-publish-gate, and rps-peer-gate. test and cli-e2e run only when that evidence is missing. release-gate then unlocks the CLI, Plus, and Inspector builds (builds do not wait for readiness). Images and Helm charts are built once and uploaded. product-smoke loads those artifacts. smoke-http3 and smoke-scripting must pass. rps-product-smoke runs on stable only. publish-gate requires release-readiness success before publish-release and the three image publishes. They push the smoked OCI layout and the smoked chart archives. Website deploy and catalog smoke run from publish-release after that gate. publish-nuget runs only after the tree guard.

    AWS lab instances are emergency-only. A beta or stable cut does not start EC2. Do not modify, stop, or delete an AWS resource older than three days.

    publish-charts.yml, chocolatey-publish.yml, and packaging-catalog-smoke.yml are manual fallbacks. They are not a second release pipeline.

    develop

    Keep lighter rules. Do not require compare-product on a feature pull request. Advisory checks (not enforced) are merge-gate, gitleaks, dependency-review, tests-or-waiver, guard-nc-paths, and cla.
