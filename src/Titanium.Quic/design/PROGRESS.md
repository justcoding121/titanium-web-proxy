Phase 2 started from the kickoff in `PHASE-2-SPEC.md`. The proxy does not call this library.

## T2.1

Variable-length integers follow RFC 9000 section 16. The shortest encoding is what this stack writes. A longer legal encoding still decodes. A truncated buffer returns false.

## T2.2

Long and short headers follow RFC 9000 section 17. A datagram is a sequence of packets until a short header, a Retry, or a Version Negotiation packet, each of which consumes the rest. A version 1 connection ID longer than 20 bytes is rejected. A Version Negotiation connection ID may be longer, because that packet quotes whatever the peer sent. A truncated header returns false. The header still exposes the truncated packet-number bytes. `QuicPacketNumber` recovers the full value.

## T2.3

Packet numbers follow RFC 9000 Appendix A. The encoder uses the appendix width: 0xac5c02 after an acknowledgment of 0xabe8b3 is two bytes, and 0xace8fe in that same state is three. A 16-bit field of 0x9b32 after 0xa82f30ea decodes to 0xa82f9b32. A two-byte field also reconstructs across 0x10000 in both directions. A candidate left outside the recovery window is rejected, as is a gap that does not fit in four bytes.

## T2.4

Initial secrets use the RFC 9001 salt and `TlsHkdf`. Client and server keys, IVs, and header-protection keys match Appendix A for connection ID `8394c8f03e515708`. AES header protection is one cached ECB encryption of the 16-byte sample. The ChaCha20 block matches the RFC 8439 block vector, and the Appendix A.5 short-header mask uses that block with the counter taken from the sample. Protect and remove are the same exclusive-or, with the packet-number length read after the first byte is uncovered.

## T2.5

The Retry integrity tag is AES-128-GCM over the pseudo-packet: the original destination connection ID length, that connection ID, then the Retry packet without its tag. The published key and nonce match the Expand-Label of the RFC secret. The Appendix A.4 sample verifies. A flipped tag is discarded, and so is a Retry whose original destination connection ID does not match.

## T2.6

Frames follow RFC 9000 section 12.4 and section 19, plus the RFC 9221 DATAGRAM types 0x30 and 0x31. Each accepted frame writes and reads back. An ACK carries ECN counts. A STREAM works with a length and without one, and so does a DATAGRAM. CRYPTO in a 1-RTT packet is legal. RFC 9000 section 17.2.2 allows an ACK in an Initial packet; an ACK in a 0-RTT packet is a protocol violation, and so is a STREAM in an Initial packet. An unknown type is a frame encoding error. ACK ranges are capped at 32. A STREAM whose offset plus length exceeds 2^62−1 is rejected.

## T2.7

Transport parameters follow RFC 9000 section 18, plus `max_datagram_frame_size` (0x20) and `grease_quic_bit` (0x2ab2). A client list and a server list, including a preferred address, round-trip. `initial_source_connection_id` is required from both sides. A server must send `original_destination_connection_id`, and `retry_source_connection_id` only after a Retry. A duplicate is a transport-parameter error. An identifier of the form 31 * N + 27 is ignored.

## T2.8

The core is sans-IO. `HandleDatagram`, `PollTransmit`, `NextTimeout`, and `HandleTimeout` take a time and a datagram. There is no socket and no timer in the core. A datagram whose destination connection ID is not already owned does not allocate a connection. Before the path is validated, bytes sent on that path stay at or below three times the bytes received, including a datagram that is attributed and then discarded. A different path has its own budget. `HandleTimeout` fires the armed deadline with no socket. The one-second deadline was a stand-in; loss recovery now supplies the real one.

## T2.9

A client and a server core complete a QUIC v1 handshake by feeding CRYPTO bytes to `TlsEngine` with datagram transport on. That mode writes the handshake without TLS records, skips the change-cipher-spec byte, and leaves the session id empty. Packet protection is AES-128-GCM with the header protection from T2.4. Initial keys come from the client's first destination connection ID. Handshake and 1-RTT keys come from the TLS traffic secrets, expanded with the QUIC labels. Transport parameters ride in extension 57. The client's first Initial is padded so the server flight fits under the three-times limit. Two cores reach the application level and exchange one STREAM byte. A bad Finished closes with a crypto error. A transport-parameter mismatch closes with a transport-parameter error. Handshake bytes above the TLS cap close with a crypto error.

## T2.10

Loss recovery follows RFC 9002. The initial RTT is 333 ms, so the first probe timeout is that RTT plus four times its variance. A packet is lost when it is three packets behind the largest acknowledgment or older than 9/8 of the RTT, and not before 1 ms. NewReno is the controller behind `ICongestionController`. Its window starts at 12,000 bytes and its floor is 2,400. Persistent congestion, three probe periods with the 25 ms acknowledgment delay included, sets the window to that floor. Pacing shares `NextTimeout` with loss detection; there is still no per-packet timer. A dropped Initial is sent again after the probe timeout. A packet acknowledged three places ahead does not by itself lose the two in between when they were just sent. An acknowledgment of a packet number that was never sent closes with a protocol violation.

## T2.11

Connection IDs, Retry, stateless reset, and path validation follow RFC 9000 sections 5.1, 8.2, 10.3, and 19.15 through 19.18. The initial connection ID is sequence 0. Retiring the last active one closes with a protocol violation. A Retry with a bad integrity tag is ignored. A good Retry changes the destination connection ID, re-derives the Initial keys from that new connection ID, and the next Initial carries the token. A `NEW_TOKEN` is stored and placed on the next connection's first Initial. A stateless reset is the last 16 bytes of a datagram that does not decrypt, compared with `FixedTimeEquals` against every used token, and it enters draining without a `CONNECTION_CLOSE`. A path challenge fills 8 bytes from `RandomNumberGenerator`, pads the datagram to at least 1200 bytes, and a matching response validates that path.

## T2.12

Streams use the peer's initial credit and later MAX_DATA and MAX_STREAM_DATA values. A send that does not fit waits, then continues when the credit grows. Data past the advertised limit closes with FLOW_CONTROL_ERROR (0x03). CRYPTO and STREAM reassembly buffer at most 16,384 bytes of out-of-order data. A larger gap closes CRYPTO with CRYPTO_BUFFER_EXCEEDED (0x0d) and a stream with FLOW_CONTROL_ERROR. RESET_STREAM and STOP_SENDING are delivered once.

## T2.13

The idle timeout is the minimum of the two advertised values, and at least three times the current probe timeout. It shares `NextTimeout` with loss recovery. A silent close discards the connection and sends nothing. A keep-alive is a PING packet, padded so header protection has a sample, and tracked by loss recovery. Receiving it restarts the idle timeout. An acknowledgment on a path that is not validated does not increase the congestion window.

## T2.14

Path MTU discovery starts at 1200 bytes. Probes are padded datagrams. A probe that is acknowledged raises the ceiling. A probe that is lost lowers the search, and a lost probe of the current ceiling returns it to 1200. A reported tunnel maximum lowers the ceiling and never takes it below 1200. Ordinary datagrams on a validated path stay at or below the ceiling. Probes are the packets that may exceed it. `DontFragment` is set on a socket where the platform allows it.

## T2.15

`UdpSocketTransport` binds an ephemeral port and exchanges datagrams with `ReceiveFromAsync` and pooled `SocketAddress` values. Callers overlap receives; four is the overlap the driver is expected to use. Linux sets `SO_REUSEPORT` when that option exists. `DontFragment` is set where the socket supports it. An outgoing ECN codepoint is set only when the socket accepts it, and a received ECN mark is not visible on this receive path. A batch send is one datagram at a time. Generic segmentation, generic receive offload, `sendmmsg`, `recvmmsg`, and a portable path-MTU socket API are not in this task. `QuicDatagramInject` feeds a datagram to a connection on a caller-supplied path and passes each reply to the callback. Amplification and path validation use that path.

## T2.16

`ManagedQuicListener`, `ManagedQuicConnection`, and `ManagedQuicStream` follow the platform connection shape. `QuicException` and `QuicError` are the platform types. The listener callback is `ManagedQuicConnectionOptionsCallback` because the platform connection type is sealed. A loopback listener on an ephemeral port completes a handshake, carries one bidirectional stream, and the payload hash matches after close. The proxy still does not call this library. Unidirectional streams are rejected. FIPS mode refuses the managed stack unless `AllowManagedStackUnderFips` or `TITANIUM_MANAGED_STACK_FIPS_OVERRIDE` is set.

## T2.17

The in-process network drops, reorders, duplicates, and delays datagrams, and it drops a datagram above its MTU. A dropped Initial is sent again after the probe timeout and the handshake still completes. Reordering and duplication do not close the connection. A delayed datagram is delivered when the clock advances. Idle timeout still fires from that clock. qlog records nothing until it is enabled. Packet and frame seeds do not throw. Negative rows are in TRACEABILITY.md. One platform client completes a handshake to the managed listener. The datagram server selects only TLS_AES_128_GCM_SHA256, which is the packet protection this library installs. The proxy still does not call this library.

## T2.18

BenchmarkDotNet on linuxmini compared this stack with System.Net.Quic. The handshake median ratio is 0.355 and the small-exchange median ratio is 0.306. Both gates are 0.90 and both are missed. The repeated bulk cell is 64 KiB because the stream window is 1 MiB and is not raised; the median ratio is 0.012, and the portable gate is only that the number is recorded. At that run `Titanium.Quic.UdpOffload` did not exist, so the 0.80 Linux offload gate was not measured. The rows are on the local-lab performance page. The proxy still does not call this library.

## CUBIC

`QuicCubic` follows RFC 9438 with the window in bytes. A loss keeps 70 percent of the bytes in flight, and the cubic increase is capped at one and a half times the current window. Fast convergence stays off because a connection is one flow. The parameterless connection still constructs `QuicNewReno`. On the in-process network a 64 KiB transfer took the same simulated time for both controllers: 5 ms with no delay, and 720 ms with an 80 ms delay. One dropped datagram at that delay closes the receiver with flow-control error 0x03 for both, because the following flight passes the 16384-byte reassembly cap. CUBIC was not faster, so it is not the default.

## UDP offload

`Titanium.Quic.UdpOffload` is the only project that calls `sendmmsg` and `recvmmsg`. A loopback probe has to accept the batch before a connection uses it, and `TITANIUM_UDP_OFFLOAD=0` forces the one-datagram send. Equal-sized datagrams can go out as one segmented send when that probe also accepts the split. A flush of more than one datagram uses the batch. Windows stays on the one-datagram send. The same linuxmini 64 KiB cell, with the batch path on, has platform median 124.8 µs (Error 22.79 µs) and managed median 12.613 ms (Error 5.563 ms). The median ratio is 0.010. The 0.80 gate is missed and is not lowered. The managed row still allocates about 139 MiB. The proxy still does not call this library.
